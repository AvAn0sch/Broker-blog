## 1. 开发策略与顺序

按现有 A–E 阶段推进，每项任务完成真实界面、接口、持久化及相关测试，不先做一套全部模拟成功的界面。优先打通“登录→保存→发布→读取”，再扩展发现、互动和治理。事务、幂等和事件基础在 A 建立，通知和治理在后续阶段复用。

```mermaid
flowchart LR
  A1[工程与跨平台环境] --> A2[数据库、事务、权限、测试基础]
  A2 --> A3[真实认证与页面骨架]
  A3 --> B1[草稿、文件、本地恢复]
  B1 --> B2[发布、阅读、发现]
  B2 --> C1[搜索与互动]
  C1 --> C2[评论、通知与任务恢复]
  C2 --> D[举报、固定快照复核、治理]
  D --> E[冻结版本、两次独立全量验收]
```

设计在 B 前明确复核快照与媒体权限，即使管理 UI 在 D 实现也不能等到 D 再重构公开内容模型。Linux 构建从 A 验证，不能推迟到交付。每阶段完成后都更新需求追踪和已知问题。

| --- | --- | --- | --- |

若 E2/E3 失败，修复并创建新 commit，再以新 commit 重做两次独立完整验收。报告可单独提交，明确“被测代码 commit”和“报告 commit”，不要求报告引用自身版本。

基础工作量合计 **44–66 人日**。另预留约 20%（9–13 人日）处理跨平台、编辑恢复和并发缺陷，总预算约 **53–79 人日**。一人每周投入 5 个有效工作日约为 11–16 周；此数只是资源假设下的换算，不排具体日期。多人投入不能直接按人数相除，数据库契约、版本模型和完整验收有串行依赖。A 结束后根据实际速度重新估算。

## 5. 测试与脚本交付合同

A 阶段落地并记录命令名称，不把下列能力描述成当前已有命令：依赖安装、启动 web/worker、数据库迁移、合成数据初始化、测试密码重置、规则测试、接口测试、浏览器测试、全量验收、报告导出、受限任务重试和资源清理。跨平台编排优先使用 Node.js 脚本，不要求 Windows 使用 Unix shell。

每轮建立唯一 run ID，推荐独立测试数据库、媒体子目录和 Compose 项目名；worker 使用该轮数据库，不能消费其他轮任务。重置时钟/故障开关/验证码适配器，使用新浏览器上下文。恢复用例的 IndexedDB 只在该用例内保留。

报告至少包含：被测 commit、dirty 状态、运行时间、run ID、环境/配置/数据集版本、依赖与浏览器版本、编号与子用例结果、首次失败原因、诊断材料位置、清理结果。敏感输入遮罩；日志不含密码、验证码、会话 token 或完整私人正文。

每个任务完成定义：需求和代码一致、相关测试通过、迁移可执行、异常路径有文字反馈、没有演示成功替代落库、文档同步、创建对应 Git commit。提交信息建议包含任务号，例如 `feat(content): B3 publish confirmed draft version`。仅提交本任务修改；已有未提交文件由原工作保留，不用全量暂存误收。

## 6. 风险与处理时点

| 风险 | 提前动作 | 不通过时处理 |
| --- | --- | --- |
| 原型与需求范围漂移 | A4 采用架构文档差异表，搜索按基线实现 | 新增功能另立变更，更新产品与用例后再排期 |
| 编辑窗口副本被覆盖、旧响应误标同步 | B2 先做双窗口、复制标签页、迟到响应测试 | 阻止发布链路进入完成态，保留复制/导出 |
| 公开/草稿/送审混用 | B1 先定三模型、DTO 和引用表 | 修复读取边界后才能做管理详情 |
| 封禁/标签停用与复核竞态 | A2 统一锁约定，D4 同步点验证 | 返回明确冲突或前置失败，不静默覆盖 |
| 文件已写、数据库未确认；清理误删 | B1 staging、上传幂等、租约与引用检查 | 恢复或安全清理，不误报上传成功 |
| worker 中断造成通知丢失或重复 | A2 事务事件，C4 租约和唯一去重 | 保留 failed 可诊断、受限重试 |
| Windows 成功但 Linux 构建/文件路径失败 | A 起持续 Linux 冒烟，固定依赖与大小写 | 阶段内修复，不留到 E |
